## Release readiness and production verification
1. Back up the live database before any migration. In phpMyAdmin select the correct database and inspect the two support tables and foreign keys. If absent, review the existing users.id type for compatibility and apply the existing support migration; do not drop or recreate tables containing data. No automatic migration is executed by deployment.
2. From the repository checkout on the server, run `php scripts/check_support_schema.php /home2/manobiki/fire.manobikishwarganj.com`. Expected exact output: SUPPORT_SCHEMA_OK. This read-only CLI checker verifies required columns, InnoDB engines and cascading foreign keys, without reading user rows or printing connection details. A failure blocks the entire scoped deployment before file copies. Correct the schema first; do not bypass the check.
3. After Flutter CI passes and the PR is merged, pull and deploy using cPanel. The scoped configuration backs up existing files, checks symlinks and PHP syntax, preserves any existing compatible premium_access.php (installs repository version only if absent), then installs the support helper, admin and API files. No database credentials or migration files are copied to the web root. Existing Career/Exam deployment remains in scope.
4. Verify unauthenticated GET /api/support/index.php returns HTTP 401 JSON, not 404/HTML; verify /support_admin.php redirects to admin login when signed out. These checks do not prove the database is ready; the CLI preflight is also required.
5. With dedicated test accounts only: open Home > Admin support; create a general ticket, reply from Admin > গ্রাহক সহায়তা, refresh the app, confirm reply, close/reopen. Verify a second test account cannot open the first ticket. If sidebar link is absent on the deployed dashboard, use the authenticated support_admin.php route and review the live dashboard version separately. Do not overwrite the live dashboard blindly.
6. Release only after full CI, preflight, deployment and authenticated end-to-end verification pass. Roll back replaced files using the dated deployment backup if needed; do not roll back database data by dropping tables.
